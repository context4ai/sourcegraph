# Snapshot synchronization and retention

Synchronization fetches depth-one snapshots of the watched branch heads. The first sync does not download their parent history. Later syncs reuse existing Git objects and add newly observed heads; commits between synchronization runs are not automatically indexed.

To prepare a specific baseline, use **Create index** with its full lowercase 40-character commit SHA, or the prepare API with that revision. Missing snapshots are fetched directly from the registered repository, without deepening its full history. The Git server must permit fetching that SHA. A rejected request fails without substituting another commit. The branch selector identifies the watched scope; it does not prove ancestry for an explicitly supplied SHA.

A snapshot prepared by SHA is an ordinary snapshot: preparation does not pin it. To work with an unmonitored branch or a tag, resolve it to a full SHA first (see [interfaces](interfaces.md#branches-tags-and-resolve)). In repository settings, **Pinned snapshots** lists the versions to keep independently of retention and capacity eviction; pins are only added there. Removing a SHA releases its pin and returns it to ordinary retention. Adding a pin alone does not fetch or index an absent snapshot: prepare the SHA first. A missing or failed index remains visible in task status.

Ordinary snapshots are retained by time since first observation, or by the configured count of most recently observed ordinary snapshots. Pins, current branch heads and commits of queued or running tasks are protected and never released. Retention runs after each successful sync and again as soon as a preparation publishes its index. When a path group reaches 4096 snapshots, the oldest unprotected one is released instead of refusing the new snapshot. Commit choices show up to 20 observed snapshots, not the complete Git history.

After a successful sync, expired snapshots lose query eligibility. Git collection then removes objects no longer reachable from any retained snapshot, preserving the complete trees and available file objects of retained versions. Index generations no retained version references are collected once their manifest is older than five minutes: right after the sync that applied retention, before a job would fail on the repository storage budget, and in a background round every minute that collects repository by repository (a repository with a running job is deferred to the next round). The status page shows pending expired indexes, deferred repositories, the last reclaim and the last issue. Adding snapshots alone does not rewrite all packs; collection runs when versions expire and periodically during synchronization. No synchronization means no automatic snapshot expiry. **Clean old indexes** keeps branch-head and pinned indexes; when a latest index is not ready it removes only expired indexes and keeps every retained version's index (`expired_only: true` in the preview).

Each repository has a **Storage budget** (default 100 GiB, configurable from 1 GiB to 10 TiB) covering Git objects, index shards and active preparation files. When it is reached, the oldest unprotected snapshots and their indexes are released, by first observation, instead of refusing work. Eviction runs only at safe points: before the Git fetch of a sync or a SHA preparation, before an index build starts (reserving 1.2 times the size of the group's previous index), and after a preparation or index task finishes. It works in batches of at most 64:

1. The batch leaves the control data in one update while holding the query lock, so reads of those versions finish first; the Git retention marker of each path group that loses versions is removed before the update commits, so collection cannot be skipped as already done; if the marker cannot be removed, nothing is committed and `RECLAIM_FAILED` is returned. They then answer `REVISION_NOT_ELIGIBLE` and can be prepared again.
2. Indexes no longer referenced are removed, then Git keeps only retained snapshots and repacks reachable objects, after checking instance free space.
3. Usage is measured again, and further batches follow until the reservation fits or nothing unprotected remains.

Failures name their cause. `REPOSITORY_STORAGE_LIMIT` means protected snapshots alone fill the budget and `SNAPSHOT_LIMIT` that they fill 4096 versions: remove pins you no longer need or raise the budget. `INSUFFICIENT_STORAGE` means the instance's free space is below its reserve, which is not the repository budget. `RECLAIM_FAILED` means collection did not finish and continues in the background. The reservation is an estimate: a running build releases nothing (its files are in use) and is refused only above 120% of the budget, always within the instance free-space reserve, and the release after it brings usage back under budget. This is a protective budget, not an exact filesystem quota, so short-lived overshoot is possible. Git compaction needs temporary working space and may exceed the repository budget while reclaiming objects.

The control data is the source of truth, and physical collection follows it idempotently. Every change that releases versions (retention after a sync or a preparation, budget eviction, the 4096 limit) removes the affected path groups' retention markers before it commits and is abandoned if that fails, and a sync reads the repository again after eviction before recording new versions; a missing marker, or one naming a released commit, means Git collection is unfinished, and only a successful collection writes it again. Besides the index round, a separate pass every minute (one at a time) checks each repository's marker and, once it holds that repository's preparation slot (busy repositories wait for the next pass), finishes Git collection using the repository's Git timeout rather than the index round's 30-second budget. Preparation and index tasks do the same before they start. An interrupted process or a failing later sync therefore does not keep released space.

`SOURCEGRAPH_MIN_FREE_BYTES` protects the instance's remaining disk space across repositories. Keep enough additional free capacity for replacement packs and index builds. Back up the control database, including pin and retention settings; Git snapshots and indexes reside on the instance volume.

Git 2.30 or newer is required for selective file hydration in path groups. The supplied production container includes a compatible Git version.
